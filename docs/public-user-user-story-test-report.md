# Public-user user-story test report

**Status:** Ready for API testing; not executed by this report.
**Actor:** An unauthenticated visitor (no `Authorization` header).
**API base path:** `/api/v1`
**Source of truth reviewed:** public controllers and services, authentication, access policy, DTO validation, and the generated OpenAPI document in `docs-json.json` (reviewed 2026-09-10).

This report turns the **Public user (unauthenticated)** section of [the user-story checklist](user-story-testing-checklist.md) into testable backend stories. It deliberately describes current implementation, including gaps and risks, rather than assuming planned product functionality exists.

## Scope and implementation summary

| Checklist capability | Current backend support | Test status |
| --- | --- | --- |
| Browse grades and catalogue hierarchy | Yes: published grades, subjects, courses, chapters, lessons, sections, and preview metadata | Covered below |
| Search, filter, and paginate catalogue | Yes: `q`, grade/subject filters, offset pagination, and cursor pagination depending on endpoint | Covered below |
| Public content preview/delivery | Yes, but only when the effective access type is `PUBLIC` | Covered below |
| Cover images and public testimonials | Yes: short-lived protected URLs | Covered below |
| Student registration and sign-in | Yes | Covered below |
| Registration geography | Yes: governorates and centers | Covered below |
| Public prices, campaign discounts, coupons | **No public endpoint.** Price preview and coupon application are student-only. | Gap |
| Referral code/link validation or registration attribution | **No public endpoint or registration field.** | Gap |
| Public locked/unlocked indicators | Partial: preview rows expose a content item's raw `accessType`; course/chapter prices and purchasability are not returned publicly. | Gap |

All error assertions should also check the standard error envelope: `statusCode`, stable `code`, localized `message`/`error`, and `correlationId`. Do not assert only human-readable English text.

## Required test data

Prepare isolated records (and retain their IDs) before beginning:

| Alias | Required state |
| --- | --- |
| `GRADE_PUBLISHED` / `GRADE_DRAFT` | One published grade and one draft or archived grade. |
| `SUBJECT_VISIBLE` / `SUBJECT_HIDDEN` | A published subject assigned to `GRADE_PUBLISHED`; a draft/archived subject or a published subject with no published-grade assignment. |
| `COURSE_VISIBLE` / `COURSE_HIDDEN` | A published course under `SUBJECT_VISIBLE`, plus unpublished and grade-ineligible variants. |
| `CHAPTER`, `LESSON`, `SECTION` | Published descendants of `COURSE_VISIBLE`, with at least two rows for ordering/cursor tests. |
| `ITEM_PUBLIC` / `ITEM_FREE` / `ITEM_PAID` | Published content at the same valid hierarchy location, each with its named effective access type; attach a ready document/image asset to `ITEM_PUBLIC`. |
| `TESTIMONIAL_PUBLISHED` / `TESTIMONIAL_DRAFT` | A published testimonial with an image screenshot and alt text, and an unpublished counterpart. |
| `GOVERNORATE`, `CENTER_VALID`, `CENTER_OTHER` | Two governorates; `CENTER_VALID` belongs to the first and `CENTER_OTHER` belongs to the second. |
| `REGISTER_*` | Unique valid Egyptian student phone, parent phone, and national ID. Keep duplicates of each for conflict tests. |

Use non-real national IDs and phone numbers generated by the approved test-data process. Never place them in source control, a test report, or a shared URL.

## User stories

### PUB-CATALOG-001 — Discover published grades, subjects, and courses

**Priority/Risk:** High — public catalogue visibility and conversion
**Sources:** `GET /academic-grades`, `GET /catalog/subjects`, `GET /catalog/courses`, `CatalogService`, `AcademicGradesService`

**User story:** As a public visitor, I want to browse the published academic catalogue so that I can decide what to explore or register for.

**Acceptance criteria:**

- Given published and unpublished grades, when `GET /academic-grades?page=1&limit=20` is called without a token, then it returns `200`, ordered published grades only, with `data` and offset `meta`; draft and archived grade IDs/titles must not occur.
- Given grade and subject names with Arabic variants, when `q` uses Arabic/English case and common Arabic character variants, then only matching published records are returned; leading/trailing whitespace is ignored.
- Given `GRADE_PUBLISHED`, when `GET /catalog/subjects?academicGradeId={GRADE_PUBLISHED}` is called, then the result contains only published subjects assigned to that grade and its `meta.total` matches the returned population.
- Given `SUBJECT_VISIBLE` and `GRADE_PUBLISHED`, when `GET /catalog/courses?subjectId={SUBJECT_VISIBLE}&academicGradeId={GRADE_PUBLISHED}` is called, then the result contains only published courses in that subject that are available through that grade assignment.
- Given invalid `page` (zero, non-integer), `limit` (zero or greater than 100), or `q` (empty/over 120 characters), when a list endpoint is called, then it returns `400` with field-level validation details and no partial result.
- Given no matching published data, when a valid query is made, then it returns `200` with `data: []` and correct zero metadata, not `404`.
- Given a malformed bearer token is supplied to `/catalog/*`, when the endpoint is called, then it returns `401`; omitting the header remains allowed. The catalogue uses optional student authentication, not anonymous-token fallback.

**Data visibility:** Returned nodes are intentionally summary data (`id`, title, slug, description, sort order, cover metadata, child hint, and where relevant raw `accessType`). They must not contain status, creator/updater, storage key, price/coupon internals, asset URLs, or private content.

**Related regression:** Admin publication and subject-grade assignment; Arabic search; optional-token handling.

### PUB-CATALOG-002 — Navigate only the published hierarchy with stable paging

**Priority/Risk:** High — unpublished-content disclosure
**Sources:** `GET /catalog/courses/:id`, `/courses/:id/chapters`, `/chapters/:id/lessons`, `/lessons/:id/sections`, `CatalogService`

**User story:** As a public visitor, I want to open a catalogue item and navigate its published descendants so that I can understand the course structure without accessing protected learning material.

**Acceptance criteria:**

- Given `COURSE_VISIBLE`, when `GET /catalog/courses/{COURSE_VISIBLE}` is called, then it returns `200` with the published subject, its academic-grade IDs, and correct counts of published chapters, lessons, and sections.
- Given an unpublished course, subject, or only draft/archived grade assignment, when course detail is requested by ID, then it returns `404` and does not disclose title, status, or ancestry.
- Given published descendants plus a draft/archived descendant, when each hierarchy collection endpoint is called, then it returns only published direct children in ascending `sortOrder`, then ID order for ties.
- Given more records than `limit`, when a child endpoint is called with `limit=1`, then `pageInfo.hasNextPage` is true and `nextCursor` is returned. When that exact cursor and the same `q` are supplied, then the next non-duplicate page is returned.
- Given a cursor altered, malformed, or reused with a different search query, when a child endpoint is called, then it returns `400 Invalid cursor` (standard envelope) rather than a wrong page.
- Given a valid but nonexistent parent ID, when a descendant endpoint is called, then it returns `404`; it must not silently return an empty collection.

**Related regression:** ordering/reorder operations, publication/archival, Arabic search, cursor encoding.

### PUB-CATALOG-003 — View content previews without bypassing content access

**Priority/Risk:** Critical — protected lesson and asset disclosure
**Sources:** `GET /catalog/{resource}/{id}/content-items`, `GET /catalog/content-items/:id`, `GET /catalog/content-items/:contentItemId/assets/:assetId/access`, `CatalogService`, `ContentAccessPolicyService`

**User story:** As a public visitor, I want to see published content previews and open explicitly public material so that I can evaluate the learning experience without receiving free or paid material unintentionally.

**Acceptance criteria:**

- Given a published hierarchy node, when its `/content-items` endpoint is requested, then it returns only published direct placements. Each preview contains only `id`, type, title, description, estimated duration, raw `accessType`, and placement order; it does not contain `textBody`, `externalUrl`, asset records, answer keys, or storage information.
- Given `ITEM_PUBLIC`, when `GET /catalog/content-items/{ITEM_PUBLIC}` is called anonymously, then it returns `200` and its delivery shape. For a text/link item this may include `textBody`/`externalUrl`; for attached media it returns asset metadata only, not a storage key or direct object URL.
- Given an asset actually attached to `ITEM_PUBLIC`, when its public asset-access endpoint is called, then it returns `200` with a short-lived `url` and `expiresAt`. An arbitrary ready asset ID that is not attached must return `403`; a nonexistent item/asset returns a safe `404`.
- Given `ITEM_FREE` or `ITEM_PAID`, when anonymous callers request either the content item or an attached asset URL, then they receive `403`. Current backend semantics are important: `FREE` still requires an authenticated active student; only `PUBLIC` is anonymous.
- Given a draft item, a draft ancestor, or an archived ancestor, when public content or asset delivery is requested directly by ID, then it must not be delivered. Draft is denied; archived requires a student retained-access snapshot and therefore is denied anonymously.
- Given a protected URL has expired, when it is used against the storage provider, then it is rejected. The API response must not expose `storageKey`, bucket, signing secret, or an unbounded URL.

**Test data / notes:** Exercise TEXT, EXTERNAL_LINK, and one asset-backed type. Verify asset bytes, not just API status. Do not attempt to infer a URL by constructing storage paths.

**Related regression:** entitlement policy, asset attachment integrity, signed delivery, archived-content retention.

### PUB-CATALOG-004 — Retrieve only visible cover images and testimonials

**Priority/Risk:** Medium — public presentation and private asset exposure
**Sources:** `GET /catalog/:resource/:id/cover/access`, `GET /testimonials`, `GET /testimonials/:id/screenshot/access`, `AssetsService`, `TestimonialsService`

**User story:** As a public visitor, I want to view published covers and testimonials so that I can assess the catalogue and platform credibility.

**Acceptance criteria:**

- Given a published visible hierarchy target with a ready IMAGE or COVER_IMAGE, when its cover-access endpoint is called with an allowed resource (`grades`, `subjects`, `courses`, `chapters`, `lessons`, or `sections`), then it returns `200` with only a time-limited `url` and `expiresAt`.
- Given no cover, a non-image cover, draft ancestry, an unsupported resource, or a nonexistent target, when cover access is requested, then it returns the expected safe `404`/`400`/`403` without an asset filename or storage key.
- Given published and unpublished testimonials, when `GET /testimonials?page=1&limit=20` is called, then it returns only published testimonials in `sortOrder`/ID order. The public summary includes review text, reviewer name, alt text, and screenshot access path, but no status/audit fields or screenshot asset ID.
- Given a published testimonial with a ready IMAGE screenshot, when the supplied screenshot-access path is requested, then it returns a short-lived URL. Draft, archived, screenshot-less, missing, or non-ready testimonial images must return `404`.
- Given pagination boundaries for testimonials, when invalid page/limit values are supplied or the last page is requested, then validation and empty-page behaviour match the shared pagination contract.

**Accessibility check:** When a screenshot is returned in a testimonial summary, `screenshotAltText` must be non-empty and the client must use it as the image alternative. This is enforced at testimonial creation; verify it remains present publicly.

### PUB-REG-001 — Obtain trusted registration reference data

**Priority/Risk:** High — registration completion and data integrity
**Sources:** `GET /geography/governorates`, `GET /academic-grades`, `GeographyService`, `AcademicGradesService`

**User story:** As a prospective student, I want to choose my published grade and an official governorate/center so that I can submit a valid registration.

**Acceptance criteria:**

- Given registered governorates and centers, when `GET /geography/governorates` is called anonymously, then it returns governorates with nested centers, ordered by Arabic name, with offset metadata.
- Given a query matching a center but not its governorate name, when `q` is used, then the owning governorate is returned with its centers; verify Arabic normalization as for catalogue search.
- Given a published grade and a draft/archived grade, when grades are listed, then only the published grade can be selected. Direct registration with the unpublished ID is rejected with `404`.
- Given `CENTER_OTHER`, when registration names `GOVERNORATE` plus that other-governorate center ID, then it returns `400 Center must belong to the selected governorate`; no user or session is created.

### PUB-REG-002 — Register a valid student safely and receive a session

**Priority/Risk:** Critical — account creation, PII, and session security
**Sources:** `POST /auth/students/register`, `RegisterStudentDto`, `AuthService.registerStudent`

**User story:** As a public visitor, I want to create a student account with valid identity, contact, location, and grade information so that I can use student-only learning and commerce features.

**Request body:** `fullName`, `nationalId`, `phone`, `parentPhone`, `governorateId`, `academicGradeId`, `password`; `centerId` is optional. The DTO requires an 8–128-character password, a non-empty string name up to 200 characters, and a national-ID input of digits/spaces/dashes before service-level normalization and validation.

**Acceptance criteria:**

- Given unique valid data, a published grade, and a matching center, when the registration request is posted once, then it returns `201`, a bearer `accessToken`, a student user summary, and an HttpOnly `refresh_token` cookie. The body must not return national ID, password, profile address data, session ID, refresh token, or password hash.
- Given phone values represented with accepted Egyptian formats, when they normalize to the same valid number, then the stored login identity and parent identity use the normalized values. Invalid student or parent phone values return `400` before account creation.
- Given malformed/empty fields, an invalid password length, invalid national-ID characters/format, missing IDs, or unknown JSON fields, when registration is attempted, then it returns `400` (or the documented `409` for service-level invalid national ID) with safe validation details and creates neither user nor session.
- Given a nonexistent/draft/archived academic grade or nonexistent governorate, when registration is attempted, then it returns `404`; given a cross-governorate center, it returns `400`; neither outcome creates an account.
- Given a previously registered normalized phone, when a new registration uses it, then it returns `409 Phone number already registered`; the same applies to normalized national-ID duplicates (`409 National ID already registered`). Retry the same successful request and verify exactly one user/profile/session lineage exists.
- Given a registration response, when its returned access token is used at `GET /auth/me`, then it identifies an active `STUDENT` account. When the refresh cookie is posted to `POST /auth/refresh`, then it rotates the cookie and returns a fresh access token; a missing/stale/replayed cookie returns `401` and no token.

**Privacy decision to confirm:** Current duplicate responses identify whether the collision is phone or national ID. They do not reveal an account name, but they do confirm that a submitted identifier exists. Product/security should explicitly approve that enumeration trade-off or replace both with a neutral registration-conflict response.

**Related regression:** student sign-in, parent linking, session rotation/replay handling, account suspension.

### PUB-AUTH-003 — Sign in as a newly registered student

**Priority/Risk:** High — handoff from public visitor to student
**Sources:** `POST /auth/students/login`, `AuthService.loginWithPassword`, shared auth routes

**User story:** As a registered student returning from the public entry point, I want to sign in safely so that I can access my protected account.

**Acceptance criteria:**

- Given the account created in PUB-REG-002, when valid phone/password are posted to `/auth/students/login`, then it returns `201` with an access token and an HttpOnly refresh cookie.
- Given an invalid phone format, when login is attempted, then it returns `400`. Given an unknown phone, wrong password, suspended account, expired/revoked session, or wrong role, then it returns safe authentication denial without exposing which credential failed.
- Given repeated failed requests, when the configured throttle is reached, then the response is `429` with `Retry-After`; a subsequent valid login follows the configured recovery window.
- Given an authenticated student, when `POST /auth/logout` is called with the bearer token and cookie, then the current session is revoked and the cookie is cleared. The old access/refresh credentials can no longer be used after their valid/revoked boundary.

### PUB-AUTHZ-004 — Deny anonymous access to private roles and protected data

**Priority/Risk:** Critical — authorization and privacy
**Sources:** global `UserAuthGuard`, `RolesGuard`, protected controllers under `/student`, `/admin`, `/partners`, and parent guards

**User story:** As the platform, I want anonymous callers blocked from private APIs so that catalogue browsing never becomes a route to private student, parent, partner, or administration data.

**Acceptance criteria:**

- Given no bearer token, when representative endpoints `GET /students/me`, `GET /student/catalog`, `GET /student/cart`, `GET /admin/students`, `GET /partners/me`, and `GET /parent/selected-child` are called, then each returns `401` (or parent-guard `401`) with no resource payload.
- Given an active student token, when an admin or partner endpoint is called, then it returns `403`; when a parent-only endpoint is called with a user bearer token, then it returns its safe parent-auth denial. The response must not reveal the target account or dataset.
- Given unauthenticated direct-ID attempts against a paid/free item, student item endpoint, student asset access endpoint, admin asset access endpoint, and admin hierarchy endpoints, then none return content body, signed URL, asset metadata, assessment/question answers, PII, or storage details.
- Given an unknown or malformed bearer token is supplied to a normally public catalogue/cover endpoint, then it returns `401` rather than treating the request as anonymous. Repeat with no header to verify valid anonymous access remains intact.

## Implementation-derived gaps and risks to triage

These are findings from static backend review, not executed failures. They should be converted to regression tests and either fixed or explicitly accepted by product/security.

| ID | Finding | Evidence / proposed test |
| --- | --- | --- |
| PUB-GAP-001 | Anonymous visitors cannot see public prices, discounts, coupons, or a calculated payable amount. | Public course summaries do not select `priceMinor`, `currency`, or `isPurchasable`; `POST /student/price-preview` is student-only. Add a public pricing contract only if this is a product requirement. |
| PUB-GAP-002 | No referral code/link can be supplied or validated before/during registration. | `RegisterStudentDto` has no referral field; referral routes are admin/partner only, while attribution occurs in student commerce. Define endpoint, validity responses, expiration/usage outcomes, and anti-enumeration rules before adding the checklist story. |
| PUB-RISK-003 | Unscoped subject/course lists can be visible without a published grade assignment, while course detail requires one. | `CatalogService.subjects()` and `.courses()` only require published subject/course when no `academicGradeId` is supplied; `.course()` verifies a published grade assignment. Test a published but unassigned subject/course and decide whether list visibility is intended. |
| PUB-RISK-004 | Public cover access does not verify a published academic-grade assignment for subject/course ancestry. | `AssetsService.coverAccess()` checks node status but not `SubjectGrade`/`AcademicGrade` status. Test cover access for a published subject/course not assigned to any published grade. |
| PUB-RISK-005 | Direct public content delivery does not verify a published academic-grade assignment. | `ContentAccessPolicyService.assertContentItemAccess()` verifies content/ancestor status and access type but does not require a published grade assignment for an anonymous request. Test a `PUBLIC` item below an unassigned published subject. |
| PUB-RISK-006 | Public subject constants are available for any existing subject, including draft/archived subjects. | `GET /subjects/:subjectId/constants` calls `publicList()`, which checks only subject existence. Test draft/archived subject IDs; restrict to published visible subjects if these values are catalogue content. |
| PUB-RISK-007 | Registration duplicate errors reveal which identifier is already registered. | `AuthService.registerStudent()` explicitly returns different conflict messages for phone and national ID. Confirm whether this is acceptable anti-enumeration behavior. |

## Completion evidence to attach when tests run

- Request/response captures with secrets, tokens, phone numbers, national IDs, signed URLs, and correlation IDs redacted.
- Database assertions for successful and failed registration attempts: user/profile count, normalized values, encrypted/hash-only national ID storage, and session state.
- A publication matrix proving draft, published, and archived behavior across catalogue listing, detail, cover, content, and asset delivery.
- Signed-URL expiry verification from the storage integration environment.
- Negative authorization results for each representative protected route, including body inspection for PII and storage data.
- Browser/UI accessibility evidence only if a frontend is in scope; this repository supplies API contracts, not public screens.
